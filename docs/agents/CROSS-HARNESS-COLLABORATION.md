- Parent #22: single cross-harness coordination dashboard (one comment updated in place), linked to workstream PRs. Current active executor, branch, exact baseline/published head, status, pending handoff, blockers, latest package and CI.
- Workstream PR: one live progress comment updated in place, with historical evidence in attributed commits, ticket comments and incremental evidence register. Parent dashboard holds concise pointers/status, not duplicated logs.

## 2. Start/resume checklist (every harness)
1. Read AGENTS.md, latest version of this protocol on integration branch, parent #22 dashboard and active workstream PR and ticket(s). Read relevant approved specification sections, not the entire history repeatedly.
2. Fetch GitHub, verify local git status, branch, remote HEAD, ahead/behind and divergence. Identify unpushed commits/uncommitted changes. Verify exact baseline and assigned ticket before editing. Preserve uncommitted work and other agents' commits; never blindly reset, stash, rebase or force push. If local work exists on an old/other branch, recover it into a separately attributed publication branch; do not reimplement without checking.
3. Publish initial checkpoint: harness/actual model/effort, workstream ID, UTC timestamp, branch, baseline SHA, local and remote HEAD, active ticket, current task, tests, blockers and next step. Take ownership of only the assigned scope. A harness change is a handoff, not a reason to repeat planning.

## 3. Atomic work cycle — one coherent change at a time
For each ticket/behavioral slice:
1. Read exact acceptance criterion and relevant diff; reproduce failure or add focused test where practical. Record observed red result; never claim red when not observed.
2. Implement smallest safe correction and run focused tests; include relevant regression tests and evidence. Keep code and its tests together in a reviewable commit (separate test-first commit allowed when explicitly WIP and safe). No unrelated formatting, scope expansion or bulk final-day commits.
3. Commit with prefix `[HARNESS][#ticket]` and descriptive summary, e.g. `[CODEX][#37] Reject invalid backup metadata` or existing `[AG-NEON][#37]`. Trailers: Executor, Model (actual or NOT VERIFIED), Effort, Workstream, Ticket, Role. Include requirement/finding IDs and test summary in body or linked evidence.
4. Push promptly after each coherent slice, not at end of session. Verify remote HEAD/commit presence with git ls-remote or GitHub API; do not equate local git commit or a claimed push with published work. Keep failures/WIP explicitly marked; don't present broken builds as accepted. If remote has moved, preserve branch and reconcile explicitly, no force push.
5. Update existing ticket evidence and workstream progress dashboard. Incrementally append concise entry to the workstream evidence register (timestamp, issue/acceptance, code SHA, reproduction, command, environment, actual result, CI link, remaining gap); commit and push evidence promptly. Avoid embedding a commit's own SHA in its content; reference the implementation SHA from the subsequent evidence commit and dashboard. Local-only private logs stay local, public/sanitized evidence and reproducible commands go to GitHub. Redact paths, credentials and operational contents.
6. Update parent dashboard when phase, owner, blocker, branch/head, package or next action materially changes. Repeat for next slice without waiting for owner confirmation unless an actual owner decision is required.

## 4. Continuous checkpoints and handoff
- Update workstream dashboard at each completed slice, test/build result, discovered issue, blocker, and at least every 15 minutes of active work if GitHub reachable. If a long operation is running, say RUNNING and name the command/CI run; don't invent progress. Checkpoint before context compaction, interruption, end of session or switch to another harness, wherever possible.
- State exact latest published SHA, local-only commit IDs, uncommitted file scope, tests PASS/FAIL/RUNNING/BLOCKED/NOT RUN, verified package digest, pending review, external blockers and next actionable task. If synchronization fails, report error explicitly; retain local checkpoint and retry at next available access. No claim of completed handoff until receiver can fetch source.
- Handoff completion gate: remote source and code/tests/evidence fetchable, exact SHA and compare range, artifact link/hash or precise local-only availability, current CI state, outstanding findings and ticket/acceptance matrix, next executor/reviewer, rollback baseline. Receiving harness verifies remote SHA/diff/test evidence before proceeding. A local-only ZIP or commit is not a shared release candidate.
- Workstream status vocabulary: NOT STARTED / IMPLEMENTING / TESTING / BLOCKED / READY FOR REVIEW / CHANGES REQUIRED / REVIEW VERIFIED / OWNER ACCEPTANCE PENDING / OWNER APPROVED. Distinguish implementation, hosted CI, independent review and actual owner UAT. Use exact evidence, not estimated overall percentages or false closure.

## 5. QA and owner gates
Keep all 46 acceptance cases; maintain ID, expected/actual, build SHA, environment, result, evidence and finding. Full regression/security/real corpus/packaged benchmark/independent review gates remain binding. Verify exact artifact and source. Reviewers record ACCEPT/CHANGES/BLOCKED with findings against immutable input, then corrective commits separately attributed. A reviewer who implements fixes cannot independently certify those same fixes. Request another independent pass for changed scope. Ticket closeout only with required evidence and authority; no legacy supersession, integration merge, production approval or cutover without owner authorization. Work/home physical UAT, actual legacy migration, native Excel clicks and mandatory performance limits cannot be waived. No new architecture or re-planning without owner decision.
